# 听芽 1.1.5（8）：原地刷新期间的任务生命周期

日期：2026-11-02（香港时间）。基线：main / `9ab1492`，1.1.4（7）。

## 用户补充与实际复现

用户明确说明“停留原页，几乎立即出现 9 个节目无法更新”。不能把这直接解释为用户切页。1.1.4 修复了取消后将未请求节目计为失败的错误，并加入真实错误详情，但尚未修复探索页手动刷新的任务生命周期。

本轮使用专用 iOS 27.1 模拟器 （设备标识已移除），在保持页面和窗口可见、不切页的条件下，实际触发 UIKit 刷新控件的 valueChanged，让它调用页面原有的 SwiftUI refreshable；不是仅直接调用 AppStore 方法。隔离数据为 13 个订阅，每个 RSS 请求延迟 40 ms，响应为可解析的科学类 RSS，探索目录返回受控空响应，不访问手机或生产资料库。

修改前：订阅页完成 13 个 RSS，请求取消 0 次；探索页只发起 1 个 RSS，请求取消 1 次，刷新中断。原始日志：`build/refresh-staying-native-probe.log`，结果包：`build/delivery/refresh-staying-native-probe.xcresult`。测试捕获的是原生刷新控件触发后的生命周期，不将它称为物理 iPhone 手指滑动验证，也不能仅凭这项实验反推用户手机当时的全部网络状态。

## 修复

探索页手动刷新改用 AppStore 持有的单个任务，不依赖短生命周期的 SwiftUI 刷新处理任务。刷新控件或页面状态更新使调用方被取消时，已经明确发起的手动更新仍能完成；重复下拉等待同一任务，不产生第二轮并行订阅刷新。完成后释放任务引用。

探索页显示“正在更新内容…”直到相关更新结束；进入页面自动更新订阅时也显示状态。普通启动／切页仍使用原有 loadHome 新鲜度和缓存判断，没有改成每次进入强制刷新。搜索仍使用独立取消通道，家长权限仍在显示和执行入口实时检查；已取消与真实失败继续按 1.1.4 分开记录。没有调整网络超时、规则、资料库 schema、存储路径、Keychain 身份、Bundle ID 或最低 iOS 16。

## 验证

修复后的原生控件测试分别覆盖：订阅页原地刷新、探索页原地刷新、进入探索页自动刷新尚未结束时再次下拉，均要求完整完成 13 个 RSS，取消 0 次，失败 0 次。

另有确定性测试：暂停首个 RSS、取消刷新控件调用方、同时发起第二个手动刷新，再恢复响应；要求订阅只更新一轮，显示状态持续到完成，原有订阅、收藏和进度保留。

最终完整 iOS hosted 回归 **130 项通过，0 失败**，日志和结果包：`build/ios-1.1.5-accepted.log`、`build/delivery/iOS-1.1.5-accepted.xcresult`。三项原地控件场景均完整请求 13 个 RSS、取消与失败均为 0；取消调用方及同时重复下拉的测试只有一轮 2 个订阅请求，原订阅、收藏与进度保持一致。独立核心测试日志为 `build/core-1.1.5-accepted.log`。保留未通过的诊断／夹具轮次。

原有性能基准继续通过：4,000 集首批本机内容发布 0.589792 s、重开就绪 0.955099 s，重开重新过滤 0 次；三次返回缓存首页 0.000697 s，全库重建与网络请求均为 0。120 项订阅首屏仍只创建 3 个封面视图。与 1.1.4 的相同测试相近，未把一次采样差值解释为性能提升，也未把 hosted 数值当作真机帧率。

1.1.4 的搜索、完整订阅栏、RSS 精确单集身份校验、家长过滤和已下载本机内容缓存保留，参见 `Docs/SEARCH_AND_SUBSCRIPTIONS_1.1.4.md`。本轮不重复声称真机通过；实际手机仍需沿用原账户、Team 和重签 Bundle ID 覆盖安装，不先卸载。
