# 听芽 1.1.3（6）：本地优先加载与家长例外反馈

日期：2026-11-01（香港时间）。基线：main / `a72c298018fee17f3f81cdb33a442292b1b300d3`，1.1.2（5）。

## 诊断与修复

现有 `@StateObject` 和五标签页的 `visited` 导航已经保留状态。本次保留该 UI 和生命周期结构，修复其下游重复工作：

- `AppStore.init` 原来在 UI actor 同步读取资料库、搜索记录、规则、拦截记录；`DiscoveryService.init` 与 AppStore 各读取一次相同的探索 JSON。下载初始化还同步解码索引、遍历本地文件、迁移音频、计算容量并重写索引。现在大文件读取、解码、文件检查和排序在后台执行，探索缓存只在 service actor 首次使用时读取一次；初始化期间禁止写入尚未读完的资料库。
- 原来普通返回首页的四个缓存命中也会调用 `revalidate`，每次重建 4,000 集展示快照；每条进度、刷新时间戳、探索部分更新也会重复取消／启动全库过滤。现改为先判断栏目新鲜度，普通切页命中直接返回；时间戳和持续进度不重建列表，进度首次进入历史、完成状态或历史顺序变化才更新集合。后台返回仍实时校验播放、队列和进行中的下载，但不会无条件重建展示。
- 原来 `episodes(for:)` 在每次读取时遍历、过滤、排序全库；现在读取现有按节目分组的展示索引。快照工作在独立 actor 合并，重复变更先合并到最新版本。节目共同的分类、发布身份和文字字段在一轮过滤中只准备一次。
- 新增可丢弃的 `display-cache.json`，只缓存**展示判定**。复用同时要求完整词库摘要、家长 policy、节目与单集元数据摘要一致，并排除时钟回拨、身份规则到期和元数据新鲜度边界。元数据更新只重算相关条目；损坏或缺失缓存会正常重新校验，不清空资料库。首次升级尚无索引时，先发布已按当前规则校验的最近更新、当前播放、队列和部分收藏／下载，再在后台完成剩余条目。不会先展示未经校验的全库。
- 资料库和下载索引的突发变更合并保存，编码和原子写入在独立 writer actor；单调 revision 防止旧任务覆盖新状态。正常启动不重写下载索引，也不再无条件重写资料库。下载页普通进入复用刚完成的文件检查，主动下拉刷新明确强制重新检查；实际本地播放仍检查文件是否存在。
- 节目详情先显示本机单集，完整且一小时内的 RSS 直接复用；过期信息在现有列表保留期间更新，手动刷新仍请求 RSS。探索与用户搜索保持独立请求通道，保留现有目录限流、失败退避、首次搜索和多目录搜索行为。
- Keychain 身份、PIN 派生参数和访问属性未改；普通浏览只使用已读入的 authority/policy，不进行重复 Keychain 查询或 PIN 派生。

本次未调整网络超时来换取表面速度，未隐藏实际更新状态，未清空资料库、卸载 App、修改词库或重新合并 B 提交。

## 家长反馈和权限边界

拦截记录详情改为独立视图，显示历史拦截原因与**当前授权状态**。点击“允许这个节目”或“允许这个单集”后，显示保存中、成功或当前页面内的失败原因；处理中禁用两个操作，成功后对应按钮显示已允许并禁用。反馈出现时自动滚动到可见位置；操作按钮自身也显示保存中。VoiceOver 会播报成功／失败，文字和图标同时提供反馈，避免只依赖颜色。

单集允许只写单集例外，节目允许只写节目例外；单集单独禁止仍优先于节目允许。安全存储写入失败或家长 grant 过期时不发布成功状态，不修改内存中的 policy。单集与节目身份不匹配时拒绝修改。

词库／policy 改变时立即清除旧展示，重新校验当前播放、队列和下载。缓存不用于播放、下载、历史点击、外链、队列执行或自动下一集的授权，这些入口仍调用当前规则的实时 gate。PIN 修改后也执行实时校验。收藏、进度等原始用户数据不会因列表过滤而删除。

## 可复核性能证据

环境：专用 iOS 27.1 模拟器（设备标识已移除），Debug hosted XCTest。固定数据：20 个节目、每个 200 集（共 4,000 集），不同长中文简介，500 条已下载索引与 500 个本地文件，500 个收藏，四个探索栏目。测试使用同一正式内置词库；模拟传输记录网络调用，不依赖公网速度。

这些是状态初始化／可展示数据发布的耗时，不能当作物理 iPhone 的屏幕帧率或音频结果。

| 操作 | 1.1.2 基线 | 1.1.3 复测 |
| --- | ---: | ---: |
| 构造 AppStore（主 actor） | 0.389 s | 0.000725 s |
| 首批已校验本地内容可展示 | 完整快照 25.221 s 后 | 1.160 s |
| 首次生成全部 4,000 集索引 | 25.221 s | 27.329 s（首次升级后台完成） |
| 新 AppStore 重开同一资料库，全部可展示 | 每次重新过滤 | 1.257 s，重新过滤 0 次 |
| 同节目 200 集列表读取 10 次 | 8.504 s | 0.000223 s |
| 返回首页并校验 3 次 | 65.768 s | 0.051135 s，全库重建 0 次 |
| 下载页普通进入（已检查的 500 文件） | 0.106 s，重复扫描 | < 0.000001 s，不重复扫描 |
| 主动检查 500 下载文件 | 同上 | 0.057343 s，明确检查 1 次 |
| 上述普通返回的网络请求 | 0 | 0 |

基线已有的“三次读取 300 集列表 < 2 秒”测试在本机耗时 2.646 秒而失败，保留原失败日志；修复后相同断言通过，没有放宽阈值。首次索引尚需后台逐集计算；这与后续跨进程缓存命中分开记录，未把首批内容耗时当作完整索引耗时。

原始证据：

- `build/performance-before.log`、`build/delivery/performance-before-run.xcresult`
- `build/performance-after-3.log`、`build/delivery/performance-after-3.xcresult`
- `build/core-tests.log`
- `build/ios-regression-1.1.3-verified.log`、`build/delivery/iOS-regression-1.1.3-verified.xcresult`

性能测试还断言普通返回不改写资料库／索引、后台返回不重建全库、持续进度不重建集合、重新加载保留进度与 500 个本地文件、缓存按元数据／policy／规则／时钟／时间边界失效。离线主动刷新失败后保留本地内容，后续普通返回不重复请求；新鲜详情不请求网络。

另在同一模拟器 OS 重新启动后，实际启动 App 并终止进程三次（不是只新建测试对象）：

| 进程启动轮次 | AppStore 起至全量状态就绪 | simctl 发起至收到就绪日志 | 重新过滤集数 |

每次均读取 4,000 集、500 条本地下载，三次间明确终止进程；资料库与下载 manifest 的 SHA256 均保持一致。证据为 `build/delivery/process-relaunch.json` 与三份 `process-relaunch-*.log`，复现脚本为同目录 `process-relaunch.py`。独立进程的 simctl 截图为黑屏，因此这些数值只证明状态层就绪，不能作为屏幕首帧或人工交互通过的证据；不把 simctl 启动开销与 hosted 对象初始化混为一项。
